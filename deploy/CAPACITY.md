# 容量基线

> 这份文件回答一个问题：**SLO 里的那些数字，依据是什么？**
>
> 现状（2026-09-29）：**热路径有实测，端到端还没有**。下面分两部分如实标注，
> 不要把第一部分当成容量结论 —— 那正是最容易犯的错（本机 16 万 QPS 就说
> 服务能扛 16 万 QPS，而真实瓶颈在上游模型的并发与延迟上，差三到四个数量级）。

---

## 一、热路径微基准（已实测）

复现：

```bash
python scripts/bench_local.py --n 40000        # 人读
python scripts/bench_local.py --n 40000 --json # 机器可读，便于留档
```

**环境**：Windows 11 (10.0.26200)，Python 3.13.12，24 核，非隔离环境（后台有其它进程）。
**样本**：每项 40,000 次；检索 2,000 次（单次贵两个数量级，满样本会主导整轮耗时）。
**取值**：3 次独立运行的中位数。

| 基准 | 单次 | 吞吐 | 说明 |
|---|---:|---:|---|
| 限流判定（加权滑动窗口，内存后端） | **6.2 μs** | ~161k/s | 每个请求一个新 IP（逼近过期清理的最坏情况） |
| 配额 claim + settle（内存后端） | **5.9 μs** | ~170k/s | 预占与结算都算（只量一个会低估） |
| 指标埋点（计数器 + 直方图观测） | **3.9 μs** | ~257k/s | 直方图格数恒为 **14** |
| 检索 + 上下文拼装 + 引用构造（tfidf，136 片段） | **658 μs** | ~1.5k/s | 热路径里最贵的一项 |

### 读出来的三件事

**1. 横切开销合计约 16 μs，不是瓶颈。**
相对"一次对话"的秒级延迟，这三项加起来占比 < 0.01%。所以限流/配额/指标都不该
被当作容量问题的第一嫌疑人 —— 排查时不要先怀疑它们。

**2. 直方图格数恒为 14，与请求量无关。**
这是固定桶设计的可观测证据（4 万次观测后仍是 14 格）。若哪天它开始随请求增长，
说明实现退回了"存原始观测值"，那是一条内存随 QPS 线性增长的路径
（一个被刷的接口即可 OOM，且 `_count` 增长看起来完全正常）。

**3. 检索是热路径里唯一值得盯的一项。**
658 μs 占 SLO 非流式目标（1 s）的约 0.07%，当前规模下无碍。
但 **tfidf 检索的代价随语料片段数增长**：每次查询都要对整个 TF-IDF 矩阵做
一次变换。语料从 136 片段涨到 10 万片段时，这一项会显著放大 ——
它是本服务**唯一已知的、随业务数据增长而变慢的热路径**。
解法是把检索后端换成向量索引（pgvector），而不是优化上面那三项。

## 二、端到端压测（**尚未执行**）

需要：一个运行中的实例 + 真实模型密钥。本机目前两者都没有，所以这一节是
**待办**，不是结论。

```bash
# 1) 起服务。压测必然撞限流，量到的会是限流器而不是服务能力 —— 先关掉
RATE_LIMIT_ENABLED=0 python -m app.serve

# 2) 不花钱：量连接与框架开销（打 /health/live）
python scripts/load_test.py --endpoint health --requests 2000 --concurrency 50

# 3) 花钱：真实对话（会调用大模型，注意费用）
python scripts/load_test.py --endpoint chat --requests 50 --concurrency 4 \
    --api-key "$SERVE_API_KEY" --yes-spend

# 4) 断连止损验证（省钱能力的直接证据）
python scripts/load_test.py --endpoint chat --requests 10 --concurrency 2 \
    --disconnect-after 3 --api-key "$SERVE_API_KEY" --yes-spend
```

⚠️ 运维脚本对 loopback **必须**关代理（`scripts/net.py` 已处理）。否则本机开着
`HTTP_PROXY` 时请求会被送进代理报 `502 upstream connect failed`，
压出来的数字会变成"经代理的吞吐"。

### 断连止损要看的两个数

压测前后的 `/metrics` 差值：

- `client_disconnected_total` **有增长** —— 服务端确实检测到了断开；
- `llm_tokens_total` **明显小于**"不打断"的对照 —— 生成真的提前停了。

只看第一条不够：检测到断开但没停生成，照样按 token 计费。

## 三、容量规划的经验式

**worker 数与副本数**：目前**没有实测依据**，`APP_WORKERS` 默认 1。
本服务是 I/O 密集（等模型吐 token），单进程异步足够撑相当并发；
真正的上限来自上游模型的并发配额，而非本机 CPU。所以先按"每副本 1 worker ×
N 副本"横向扩，而不是调大 worker 数 —— 后者会让每个进程各持一份缓存与
限流器状态（多副本共享后端是靠 Redis 解决的，见 `PRODUCTION_CONFIG.md`）。

**限流阈值的依据**：`RATE_LIMIT_PER_MINUTE` 默认 120/分钟/IP。这是**按单用户
正常使用节奏估的**，不是压出来的。端到端压测后应回填：如果单副本在饱和前
能服务 X req/s，且目标用户数 N，则阈值应满足"正常用户不受影响、异常用户
不过度消耗上游配额"。

**SLO 延迟目标的依据**：`deploy/monitoring/SLO.md` 定的是"非流式接口 99% ≤ 1 s"。
按上面第一部分的实测，框架内开销约 0.67 ms（检索 658 μs + 横切 16 μs），
**其余全部是模型时间**。所以这条 SLO 实际上是在约束上游模型的响应速度 ——
端到端压测要专门记录"模型首 token 时间"与"完整生成时间"两个分量，
否则超标时分不清该找谁。
