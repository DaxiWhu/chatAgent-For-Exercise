# 幂等键规范（`Idempotency-Key`）

**这份文档是对客户端的承诺。** 它按 IETF 草案
`draft-ietf-httpapi-idempotency-key-header-07` 写成，并**逐条**对照实现
（`app/idempotency.py` + `app/main.py` 的 `_idempotency_gate`）。改代码就要改这里。

> 为什么必须写它：草案 2.5.2 对资源方用的是 **MUST** ——
> "Resources MUST publish a idempotency related specification. This specification
> MUST include expiration related policy if applicable."
> 不发布的后果不是"少一份文档"，而是客户端只能靠猜：猜重试该带什么、猜什么时候
> 该换键、猜键能用多久。猜错的表现是"重试被 409 挡住"或"以为去重了其实没有"。

---

## 一、适用范围

带 `Idempotency-Key` 请求头时，下列操作按本文的语义执行（旧路径别名等价）：

| 操作 | 说明 |
|---|---|
| `POST /v1/chat` | 启动一轮 SSE 流式对话（**主要场景**） |
| `POST /v1/review` | 人工审核 resume，续跑被挂起的图 |
| `POST /v1/chat/resume` | 续跑一条中途断掉的会话 |
| `POST /v1/sessions/{id}/messages` | 任务执行中补一句话（写会话历史，不触发运行） |

`POST /chat` / `POST /review` 是它们的兼容别名，行为完全一致。

**其他端点不受影响**：`GET` 本来就幂等，`DELETE /v1/sessions/{id}` 也是幂等的
（重复删同一会话结果相同）。本文只覆盖上面四个 POST。

判据不是"会不会烧 token"，而是**"重试会不会产生第二次副作用"**：
`/messages` 不生成任何内容、不占配额，但重试会往会话历史里再写一条 ——
模型会把它当成用户说了两遍，于是把同一句要求当两次强调去执行。
这类"重放没有收益、重复有代价"的写操作，都在本文覆盖范围里。

**不带这个请求头时，行为与没有这套机制完全一致** —— 不去重、不报错、不拦截。
（是否强制要求该头见 §五的第 4 条。）

---

## 二、客户端要做的事

1. **每次"新请求"生成一个唯一的键**，放进 `Idempotency-Key` 请求头。
   推荐 UUID v4 或等价的随机串（草案 2.2 的 RECOMMENDED）。
2. **重试时必须带同一个键**，且**请求体必须逐字节等价**（见 §四的指纹口径）。
   换键 = 服务端视为"另一次请求"，会真的再跑一遍并再计一次费。
3. **不要跨不同载荷复用同一个键**（草案 2.2 的 MUST NOT）—— 会被拒（422）。
4. **键的语义是「这一次请求」，不是「这个问题」**：用户确实想再问一遍同一个问题时，
   生成一个新键即可。服务端**不会**按消息内容去重（那是刻意的：按内容去重会把
   正常行为误判成重试，属于功能损坏）。

## 三、服务端判定表

判定依据是 **(键, 请求指纹)** 这个组合：

| 情形 | 服务端行为 | 对客户端意味着 |
|---|---|---|
| 键与指纹都没见过 | 正常执行（草案 2.6 First time request） | 与不带键完全一样 |
| 键、指纹都见过，且上一次**已完成** | **重放上一次的完整响应**（2.6 Retry） | 拿到与首次**逐字节一致**的流；不会产生新的 token 消耗 |
| 键见过，且上一次**仍在处理中** | `409`（2.6 Concurrent Request） | 上一次还没结束，稍后重试 |
| 键见过，但**指纹不同** | `422`（2.7） | 你把同一个键用在两个不同请求上了，换新键 |
| 键格式非法 / 缺键且服务要求 | `400`（2.7） | 见 §四、§五 |
| 键过期后再来（超过保留时长） | 视为**首次**（正常执行） | 此时不再有去重保护 —— 见 §六 |

**重放的响应带 `Idempotency-Replayed: true`**，并回显该次生成时的
`X-Prompt-Version`。客户端可以据此区分"这次真的调了模型"与"只是把上次的结果又发了一遍"。

> ⚠️ 重放的是**事件序列**（token 分段、citations、citation_check、need_review、
> done 全都在），不是"把最终答案拼成一条 token"。前端的分段渲染、引用面板、
> 审核弹窗都不需要为此改任何东西。

## 四、键的格式与请求指纹

### 键

- 长度 ≤ `IDEMPOTENCY_MAX_KEY_CHARS`（默认 128）。
- 只接受**可打印 ASCII**（`0x21`–`0x7E`），且**不含引号与反斜杠**。
  这条不是为了好看：键会进缓存键（服务端用 `\x1f` 分隔租户与用户）与日志 ——
  允许控制字符就能伪造别人的键前缀、或往日志里注入换行（草案 §5 的
  "Injection attacks" 与 "Data leaks"）。
- 草案 2.1 规定该头是 Structured Header（RFC 8941），其 String 形式**带引号**
  （`Idempotency-Key: "8e03978e-…"`）。服务端**两种都收**：整体被一对引号包住时会剥掉引号。
  不做 RFC 8941 的转义反转义 —— 含转义序列的键会被判为格式非法（400）。
- 服务端的复合键是 **`(租户, 用户, 键)`**，三者缺一不可（草案 §5 的 "composite key"）：
  - **按租户隔离**：两个租户可以用同一个键名，互不干扰；
  - **按用户隔离**（`2026-10-06` 起）：同一个租户里的两个账号用同一个键名同样互不干扰。
    少了这一层，同租户的 B 只要拿到 A 用过的键名就能**按住 A 的请求**
    （A 收到 409「正在处理中」），或在 A 完成之后用同键同载荷**拿到 A 那次的回答正文**
    （`Idempotency-Replayed: true`）—— 两者都不需要任何越权凭证。
    这也与配额分桶、会话归属的 `(tenant, user)` 口径保持一致。

### 请求指纹

- 算法：**规范化 JSON 的 SHA-256**（草案 2.4 列举的第一种做法：整个请求载荷的校验和）。
- 参与字段：`op`（操作名 `chat` / `review` / `resume` / `session_message`）+ 该操作的
  **完整请求体**。
- ⚠️ **在路径里而不在请求体里的参数，也必须并进指纹**：`POST /v1/sessions/{id}/messages`
  的 `thread_id` 就是这种情况。不并的话，"同一个键、两个不同会话、同样一句话"
  会被判成同一次请求并**重放** —— 客户端以为写进了 B，实际只有 A 有，且没有任何报错。
- 规范化是 `sort_keys` 的 ⇒ **字段顺序变化不影响指纹**（不同语言的 JSON 序列化顺序不同，
  这点必须宽松，否则客户端换个 SDK 就会莫名收到 422）。

## 五、错误响应

全部用 `application/problem+json`（RFC 9457）：

```json
{
  "type": "<IDEMPOTENCY_DOC_URL 或其回落值>",
  "title": "Idempotency-Key 已被用于不同的请求载荷",
  "status": 422,
  "detail": "同一个键不能跨不同载荷复用（草案 2.2 的 MUST NOT）。若确实是另一次请求，请换一个新的键。"
}
```

| 状态码 | 触发条件 | 处置 |
|---|---|---|
| **400** | 键格式非法；或服务声明该头必需而请求没带 | 按 §四 修正键；或改为必带（看服务端配置） |
| **409** | 上一次仍在处理中（`in_flight`）；或上一次已完成但响应不可重放（`not_replayable`） | 前者稍后重试；后者改用 `GET /v1/sessions/{thread_id}` 取结果 |
| **422** | 同一个键被用于不同的请求载荷 | 换一个新键（这是客户端 bug，服务端行为正确） |

第 1 条里"服务声明该头必需"由服务端配置决定（`IDEMPOTENCY_REQUIRE_KEY`）：
默认**不要求**（草案 2.5.1：带不带是客户端的自由）。开启后缺失/非法一律 400 且
响应体带指向本文档的链接（草案 2.7 的 SHOULD）。**生产环境是否要求，以服务端公布的
配置为准** —— 启动日志的 `idempotency.require_key` 是权威答案。

## 六、过期策略（草案 2.3 要求公布的那一项）

- 键与**重放内容**保留 `IDEMPOTENCY_TTL_SECONDS` 秒，默认 **600 秒（10 分钟）**，
  自该请求**首次登记**起算，**不续期**。
- 过期后：键被清除 ⇒ 同键重试被当成**首次请求**正常执行，**不再有去重保护**，
  且**不会有任何报错**。所以客户端的重试窗口必须**短于**这个时长。
  服务端默认值（10 分钟）按"网关 30s 超时 + 客户端指数退避重试几次"这一整段来定。
- 单进程内最多登记 `IDEMPOTENCY_MAX_ENTRIES` 个键（默认 10000）。达到上限后
  **不再登记新键**（已登记的仍然生效）—— 这是"宁可少一层保护，也不让键表把内存吃光"
  的取舍，日志里有一条 warning。

## 七、与草案的三处**刻意**差异

写在明面上，方便客户端预期：

1. **失败/中断的请求不占用键**：请求失败、客户端断连、被配额拒绝时，键会被撤销，
   客户端可以用**同一个键**重试。草案 2.6 说重复请求"SHOULD respond with the result
   of the previously completed operation, **success or an error**"——本项目**不缓存错误
   结果**。理由：一次上游抖动被缓存下来，会让客户端在整个保留窗口内再也拿不到结果，
   而它重试的逻辑完全正确。这条偏离对客户端是**更宽松**的（重试一定能重新执行）。
2. **`409` 的第二种用法**（`not_replayable`）：草案用它表示"在途冲突"。本服务在
   "已完成但响应超过重放上限、没能缓存下来"时也回 409，并在 `title` 里写明区别。
   客户端遇到 409 的通用处置（去 `GET /v1/sessions/{thread_id}` 看）对两种都成立。
3. **回放的上限**：单个键最多缓存 `IDEMPOTENCY_MAX_BODY_BYTES`（默认 256 KiB）。
   超长回答不会被缓存 ⇒ 那次同键重试回 409（而不是重放）。这是内存上界的必然代价：
   键由客户端提供，缓存无上界就等于开了一个内存放大面。

## 八、多副本与依赖

- 配了 `REDIS_URL` ⇒ 键表在 Redis（`SET NX EX` 原子抢占），**跨副本有效**。
- 没配 ⇒ 键表在**进程内**：重试落到另一个副本仍会**重复执行**（保护失效，且无报错）。
  启动日志的 `idempotency.backend` 会如实回显 `redis` / `memory`。
- 存储故障（Redis 抖动）时服务端**放行**该请求（降级取向与限流/配额一致）：
  幂等是尽力而为的额外保护，不该因为缓存故障把正常请求打死。

## 九、排障用的指标

| 指标 | 含义 | 该看什么 |
|---|---|---|
| `idempotency_replay_total` | 被**正确吸收**的重试次数 | 这是这套机制省下来的生成次数 |
| `idempotency_conflict_total{reason="in_flight"}` | 客户端等不及就重试了 | 对照延迟指标：是不是请求比客户端超时窗口更慢 |
| `idempotency_conflict_total{reason="not_replayable"}` | 已完成但响应没能缓存 | 配合 `idempotency_truncated_total` 调 `IDEMPOTENCY_MAX_BODY_BYTES` |
| `idempotency_mismatch_total` | 同键换了载荷（422） | **客户端 bug**，服务端行为正确 |
| `idempotency_rejected_total{reason}` | 键缺失/格式非法（400） | 接入事故：客户端没按本文档带键 |
| `idempotency_truncated_total` | 缓存正文失败（超限/过期/写入失败） | 对客户端可见的行为差异（重放 → 指路），别只在日志里 |

处置流程见 `RUNBOOK.md` 的 `IdempotencyConflictsHigh` 条目。
