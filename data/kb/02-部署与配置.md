# 部署与配置

## 配置的唯一来源

`app/` 下读取环境变量一律走 `app/config.py`，只有两处例外：
`DB_URL` 在 lifespan 与迁移 CLI 中读取，`APP_*` 在 `app/serve.py` 的 argparse 中读取。

两条配置原则：

1. **要外部填的（密钥、外部地址、配额）默认必须是空或 0**，不能给一个看起来能用的默认值。
2. **能力开关默认打开，但「开着且没配」时的行为必须与关闭时一致**，不能因为多了一个开关就改变默认路径。

安全开关必须登记进 `config.as_dict()`，否则它不会出现在启动日志回显里，
运维就没有办法确认「我填的到底生效了没有」。`as_dict()` 只用于启动日志，不通过 HTTP 暴露。

## 关键环境变量

| 变量 | 含义 |
| --- | --- |
| `APP_ENV` | 设为 `production` 时关闭 `/docs`，并启用生产启动守卫（缺 `AUTH_*`、或环境里残留已删除的 `SERVE_API_KEY`/`REQUIRE_AUTH` 键，都拒绝启动） |
| `DB_URL` | PostgreSQL 连接串；不配则检查点退化为内存，重启丢状态 |
| `AGNES_API_KEY` | 模型服务的密钥 |
| `AGNES_MODEL` / `AGNES_API_BASE` | 模型名与接口地址 |
| `DOCS_DIR` | 语料目录，容器内默认 `/app/data` |
| `RATE_LIMIT_ENABLED` | 限流总开关 |
| `TRUST_PROXY_HEADERS` | 是否信任反向代理传来的客户端 IP |
| `USER_DAILY_TOKEN_QUOTA` | 每租户每日 token 上限，`0` 表示不限 |
| `LLM_MAX_TOKENS_PER_REQUEST` | 单请求 token 预算，`0` 表示不限 |
| `REQUEST_TIMEOUT_SECONDS` | 请求级总超时，`0` 表示不限 |
| `GRACEFUL_SHUTDOWN_TIMEOUT` | 优雅关闭等待在途请求的秒数，默认 30 |
| `REDIS_URL` | 多副本时共享限流与配额计数 |
| `APP_WORKERS` / `WEB_CONCURRENCY` | worker 数，取值优先级高于 1 的默认值 |

## worker 数的单一来源

worker 数由 `serve.resolve_workers()` 决定，优先级为 `APP_WORKERS` → `WEB_CONCURRENCY` → 1。

Dockerfile 的 `CMD` 里**刻意不写 `--workers`**：命令行参数的优先级高于环境变量，
一旦写死就会静默覆盖 `.env` 里的配置，导致「我明明配了 4 个 worker 却只有 1 个」。

## 反向代理下的注意事项

`TRUST_PROXY_HEADERS` 默认为 `False`，这个选择在两个方向上都可能出错：

- 部署在反向代理后面却设为 `0`：限流按代理自身的 IP 统计，**全体用户共用一个计数桶**，
  要么集体被误伤，要么被单人吃满。
- 直连却设为 `1`：客户端可以伪造 `X-Forwarded-For` 来换桶，限流形同虚设。

只读路径必须使用 `owner_of` 这类无副作用的查询，不能用会写入归属的操作，
否则「先读一次」就能抢占别人的 `thread_id`。多租户下查不到属主时返回 **404** 而不是 403，
避免暴露「这个 id 到底存不存在」。

## 容器部署

两个应用服务 `app-stable` 与 `app-canary` 都必须设置三项资源上限：

- `memory` —— 对应 OOM，且 OOM killer 挑选牺牲进程是不确定的
- `cpus` —— 防止卡死的解析任务跑满 CPU 拖垮同机其它服务
- `pids` —— 防止 fork bomb 或线程泄漏耗尽宿主机 PID 表

同时需要 `cap_drop: ALL` 与 `security_opt: no-new-privileges:true`。
灰度副本（canary）拿到的资源**不得多于**稳定版——否则一次灰度事故会连带影响全部用户。

**镜像刻意不打包 `data/` 目录**（体积大、随业务变化、不该因为换语料就重建镜像），
所以必须通过 compose 把语料目录挂载到 `/app/data`，并且**不能挂成只读**，
因为解析缓存需要写入 `<语料目录>/.parse_cache`。

不挂载的后果不是报错，而是一次**静默失败**：服务正常启动、探针全绿、SSE 也能连上，
只是检索永远召回 0 条、回答里没有任何引用。

## 优雅关闭

uvicorn 对响应尚未结束的连接只会设置 `keep_alive = False` 并等它写完，
**不会掐断在途的 SSE**。真正的风险来自两处：

1. uvicorn 的 `timeout_graceful_shutdown` 默认为 `None`，也就是永远等待；
2. 容器按自己的宽限期收场。`docker stop` 默认 10 秒，超时即 SIGKILL，
   而被 SIGKILL 才是真的掐断，且不留下任何清理机会。

因此 `GRACEFUL_SHUTDOWN_TIMEOUT`（默认 30 秒）与 docker-compose 的 `stop_grace_period`（45 秒）
**必须联动配置，且后者要大于前者**。只改一处等于没改。

在途请求数通过 `middleware.in_flight_count()` 暴露为 gauge `http_requests_in_flight`，
关闭时由 lifespan 播报。
