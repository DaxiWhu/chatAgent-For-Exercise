# 限流与配额

服务有两道互相独立的闸门：**限流**防的是请求频率，**配额**防的是 token 消耗。
两者都按租户与来源 IP 维度统计，且都支持在多副本间共享计数。

## 限流：加权滑动窗口

限流的判定值不是一个整数计数，而是一个加权值：

```
判定值 = 上一窗口计数 × 剩余比例 + 当前窗口计数
```

之所以不用固定窗口，是因为固定窗口按整分钟翻转，在「窗口末尾用满额度、窗口开头再用满额度」
时，任意 60 秒内实际会放行 2 倍的额度。而且一个按 60 秒对齐的重试循环会稳定命中这个缺陷。

也不用令牌桶或滑动窗口日志：

- 令牌桶的状态是「上次补充时间 + 令牌数」，多实例下要么上 Redis Lua 脚本，要么接受竞态；
- 滑动窗口日志（记录每一次命中的时刻）每键内存随流量线性增长，是一个可被利用的内存放大面，
  等价于内存型拒绝服务。

加权滑动窗口的内存仍是每键 O(1)，两个后端（进程内与 Redis）使用同一套语义。

### 关于 Retry-After

`Retry-After` 必须给「重试这一次」留出 1 个配额。判定要包含本次请求，
恢复时刻的计算也必须包含本次；否则算出来的时间会早一步，客户端按它重试又被拒绝，
形成重试风暴。因此计算恢复时刻时会先用 `limit - 1` 作为可用预算。

### Redis 键的 TTL

Redis 下限流键的 TTL **必须覆盖两个窗口**（即 `2 × 窗口 + 1` 秒）。
只给一个窗口时，键恰好在下个窗口开始时过期，「上一窗口」被读成 0，
固定窗口的那个边界缺陷就会原样复发——而且只在多副本且跨窗口的瞬间出现，极难复现。

## 配额：claim 到 settle 的两阶段协议

配额不能采用「请求开头检查、请求结尾累加」的写法。两次操作之间隔着整次生成，
耗时从几秒到几十秒；并发的 N 个请求会各自读到同一个「还没超」的旧值后一起放行，
于是日额度会被超掉 N 份，这是典型的 TOCTOU 缺陷。

正确做法是**先占后判**：

1. `claim()` 原子地完成「预占」与「判定」。预占量等于单请求上限
   （`LLM_MAX_TOKENS_PER_REQUEST`，未配置时为 1）。如果加上预占后越界，就把预占退回并拒绝。
2. `settle()` 在请求结束时，把预占量换成实际消耗量。

两个细节必须守住：

- **`add` 必须接受负数。** 如果实现里写成「等于 0 才早返回」以外的短路逻辑，
  退还就会被静默忽略，`settle` 变成空操作，额度只减不增。
- **预占必须由 SSE 响应构造处发出**，不能放在前置校验里。因为 `/review` 与 `/resume`
  的 409 会在进入生成之前返回，而退还只发生在生成器的 finally 中；
  把预占放在校验里必然导致额度永久泄漏。

会话归属校验仍然留在前置校验中，并且排在业务校验之前，防止被用来做枚举探测。

### 跨天退还

如果预占发生在昨天、结算发生在今天，差额会打到今天的计数键上。
因此两个存储后端的 `add` 结果都要**以 0 为下限截断**，否则今天的用量会变成负数，
等于白送额度。

### 后端故障时的行为

共享后端（Redis）不可用时，限流与配额都**退回到进程内计数**，而不是放行。
放行等同于闸门失效；不计数则意味着额度永远攒不满，同样失去意义。

后端在构造期必须真正 `ping()` 一次——`from_url` 是懒连接，不会真的建连，
如果不主动探测，就会把「配了但连不上」误判为「已经在用」。

配额的 TTL 使用相对过期时间并带下限（`max(60, ...)`），不使用依赖两侧时钟一致的绝对到期时间。

## 配置错配的自检

如果日额度大于 0，而单请求预占上限已经大于等于日额度，
那么任何请求的预占都无法被容纳，所有请求都会被判 429。启动时会检测这种错配并打告警。

## 相关指标

限流与配额都在 `/metrics` 上暴露计数器：`rate_limited_total`（按维度打标签）、
`quota_exceeded_total`。两者配合 `http_requests_total{status="429"}` 可以区分
「是被频率闸门拦的」还是「是被额度闸门拦的」。
