# 可观测性与 SLO

## 日志

日志使用结构化 JSON 输出（`app/logging_setup.py` 的 `JsonFormatter`），
便于日志系统做字段提取与聚合；也可以通过配置切成纯文本格式方便本地阅读。

用户消息正文与草稿正文**都不写入日志**。审核动作会留审计记录，但日志里只记
操作者、来源与意见的字符数，不记意见正文——审核意见常常包含业务敏感信息。

## 指标

`GET /metrics` 输出 Prometheus 文本格式（`text/plain; version=0.0.4`）。
主要指标包括：

| 指标 | 类型 | 说明 |
| --- | --- | --- |
| `http_requests_total` | counter | 按 method / path / status 打标签 |
| `http_request_duration_seconds` | histogram | 请求耗时，使用固定桶 |
| `llm_tokens_total` | counter | 累计消耗 token |
| `llm_tokens_per_request` | histogram | 单请求 token 消耗分布 |
| `review_pending` | gauge | 当前待审核积压量 |
| `client_disconnected_total` | counter | 客户端提前断开次数 |
| `rate_limited_total` | counter | 被限流拦截次数，按维度打标签 |
| `quota_exceeded_total` | counter | 被配额拦截次数 |
| `tenant_mismatch_total` | counter | 租户与 Key 不匹配（越权尝试） |
| `session_owner_mismatch_total` | counter | 会话归属不符（猜测会话 id） |
| `request_timeout_total` | counter | 请求级总超时触发次数 |
| `http_requests_in_flight` | gauge | 在途请求数，关闭时用于播报 |

### 直方图为什么用固定桶

直方图采用**固定桶计数**，每一格存一个整数，内存占用是 O(桶数)、与请求量无关。

如果改成把每次观测的原始值追加进列表，内存就会随 QPS 线性增长——一个被刷的接口
就能把进程撑爆，而且 `_count` 的增长看起来完全正常，没有任何指标能反映这个问题。

桶的语义是**累积**的：`le` 表示「小于等于」，因此落桶要用二分查找找到第一个
「大于等于该值」的边界。用错了会系统性偏移一格。

### 标签基数

`path` 标签必须使用**路由模板**而不是原始路径。请求体积闸门在路由之前返回，
此时拿不到路由模板，必须写固定的占位值；否则攻击者只要填一个任意路径就能把标签基数打爆。

## SLO 与错误预算

SLO 的定义文件是 `deploy/monitoring/SLO.md`，它是唯一事实源；
`alerts.yml` 里 `chatagent-slo` 组的表达式是它的实现，两者在测试中逐行对齐，
只改一处会立刻测红。

### 为什么要 SLO 而不是只有阈值告警

阈值告警只能回答「此刻是不是坏了」，对两类真实故障几乎无感：

- **慢刀子**：错误率长期稳定在 6%，每个瞬时窗口都没超红线，但一个月下来已经违约；
- **尖峰后遗症**：一个 20 分钟的错误尖峰过去后瞬时错误率早已回落，
  但它烧掉的预算已经回不来了。

SLO 把问题换成「按这个速度烧下去，月底还够不够」，用**燃尽率**度量：

```
燃尽率 = 实际错误率 / (1 - SLO 目标)
```

燃尽率为 1 表示不快不慢、刚好在窗口末把预算用完；
燃尽率为 14.4 表示 1 小时烧掉 30 天预算的 2%，约 8.6 小时烧光，必须立刻处置。

### SLI 口径

| SLI | 事件 | 好事件 | 坏事件 |
| --- | --- | --- | --- |
| availability | 一个 HTTP 请求 | 状态码非 5xx | 状态码 5xx |
| latency | 一个**非流式** HTTP 请求 | 耗时 ≤ 1 秒 | 耗时 > 1 秒 |

4xx、429、413 属于我们主动拒绝，不计入可用性故障。

延迟 SLI **只统计非流式请求**：流式接口的耗时等于整段生成的时长，算进来会让该 SLI 恒不达标。

⚠️ 可用性 SLI 的分子不要用 `http_errors_total`。它只在未捕获异常时自增，
像就绪探针返回 503 这类「正常返回的失败」不计入，拿它当分子会系统性低估错误率，
SLO 会看着永远达标——这是最危险的一种错。正确口径是 `http_requests_total{status=~"5.."}`。

⚠️ 标签值格式必须与指标实际渲染一致：桶边界渲染为 `le="1.0"`，而 PromQL 是全串匹配，
规则里写成 `le="1"` 会让告警永不触发且没有任何报错。

### 目标与错误预算

窗口为 30 天：

| SLI | 目标 | 错误预算 |
| --- | --- | --- |
| availability | 99.5% | 0.5% |
| latency | 99.0% 非流式请求 ≤ 1 秒 | 1.0% |

### 多窗口多燃尽率

燃尽率告警必须**长窗口与短窗口同时成立**（用 `and` 连接）：

- 只看长窗口：已经过去的尖峰会让告警继续挂很久，恢复慢、误报长，值班的人很快开始忽略；
- 只看短窗口：30 秒抖动就能把人叫醒，同样是噪音；
- 两者同时要求：既证明长期确实在烧，也证明此刻还在烧，这才值得叫人。

现有 5 条规则覆盖 availability 的 14.4 / 6 / 1 倍燃尽率与 latency 的 14.4 / 1 倍燃尽率。

### 告警路由

告警按 `category` 标签分为四类并路由到不同接收人：

- `security` —— 立即通知，这类指标平时恒为 0，一旦非 0 就是正在被攻击；
- `availability` —— 尽快通知，服务不可用需立刻处理；
- `cost` —— 攒批，当天处理即可，每条都秒推会让人对告警脱敏；
- `slo` —— 复用值班接收人。

⚠️ 规则组名**不会**自动变成告警标签，必须逐条写 `category`，否则路由匹配不到。
另外 `prometheus.yml` 如果缺少 `alerting.alertmanagers` 配置，
规则照样 firing、面板上一切正常，但事件**从不外发**——这是最容易误导的静默故障。

## 已知局限

1. 指标是单进程的，多 worker 或多实例下每个进程各算各的；表达式用 `sum(...)` 跨实例聚合，
   只对全局错误率负责。
2. 没有录音规则，SLI 表达式在每条告警里内联重复，改口径要改多处。
3. 抓取间隔为 30 秒，5 分钟窗口只有约 10 个采样点，更短的窗口会因采样太少而抖动。
4. 燃尽率告警是速率告警，对「预算还剩多少」无感；若要「预算不足时提醒」需要另加规则。
