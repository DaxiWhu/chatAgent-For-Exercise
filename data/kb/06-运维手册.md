# 运维手册

## 数据库迁移

结构变更由 `app/migrations.py` 管理，当前代码期望的结构版本记录在 `SCHEMA_VERSION` 常量里。
迁移是按编号顺序执行的幂等操作，已执行过的会被跳过。

用 `python -m app.migrations --status` 检查状态：正常时退出码为 0；
缺少迁移或向量维度不符时返回非 0，可以直接用作上线前的门禁。

现有迁移包括向量表、审核队列表、会话归属表，以及审核审计列。
审核表新增列时采用 `ADD COLUMN IF NOT EXISTS` 补列，因此老库可以原地升级，不需要重建。

## 备份与恢复演练

脚本是 `scripts/pg_backup.py`，支持备份、列出、校验、恢复与**演练**五个子命令。

演练是必需品：「没被恢复过的备份不算备份」。你可能拿到一个权限不足、版本不匹配，
或者恢复出来少了一半表的 dump，而这一切只有在真的需要它的那天才会暴露。

```
python scripts/pg_backup.py backup          # 备份到 backups/
python scripts/pg_backup.py list            # 列出已有备份
python scripts/pg_backup.py verify 文件      # 只校验文件完整性，不恢复
python scripts/pg_backup.py restore 文件 --yes
python scripts/pg_backup.py drill           # 备份 + 恢复 + 逐表行数比对 + 清理
```

执行 pg_dump 时按优先级自动选择：优先在容器内执行（容器里自带与 PostgreSQL 版本严格匹配的
客户端，也不受宿主机环境影响），其次用宿主机的 pg_dump。**两者都选不到时报错而不是静默跳过**，
静默跳过会让人误以为备份成功了。

数据库端口绑定为 `127.0.0.1:5433`。必须是回环绑定：默认的 `5433:5432` 等价于监听所有网卡，
在云主机上就等于把一个已知弱口令的数据库开放给整个互联网。

## 灰度发布

compose 里定义了两个应用服务：`app-stable` 与 `app-canary`，
nginx 按权重分流（默认 9:1）。

灰度副本拿到的时间比例很小，因此**不应该比稳定版拿到更多资源**——
否则一次灰度事故会连带影响那 90% 的用户。

指标里带 `release` 标签可以区分 stable 与 canary，回滚时据此判断影响面。
灰度判定不能靠调用方自己选版本，那样就变成双写而不是灰度了。

## 上线前自检清单

按顺序确认：

1. `APP_ENV=production` 已设置，并清楚它会关闭 `/docs`。
2. **用户鉴权已启用**：`AUTH_SESSION_SECRET` 非空，启动日志 `user_auth.enabled=True`，
   且 `accounts.backend` 是 `postgres`（是 `memory` 则账号只在单进程内存里）。
   生产环境**没启用用户鉴权**会**拒绝启动**；`AUTH_REVIEWER_ROLES` /
   `AUTH_ADMIN_ROLES` 默认 fail-closed（`reviewer` / `admin`），留空等于没人能做。
3. 环境里**没有** `SERVE_API_KEY` 与 `REQUIRE_AUTH` 这两个键（留空也算有）。
   它们已整体删除，残留会让服务**拒绝启动** —— 这正是"以为后门还关着、其实还在"的防线。
4. 第一个管理员已存在，用错误密码调 `/v1/auth/login` 确实返回 401，正确密码能拿到令牌。
5. **没有任何凭证能绕过鉴权**：裸请求（不带 `Authorization`）调 `/v1/admin/users`
   返回 **401**；带上 `X-API-Key: 任意值` 也返回 **401**（该请求头已不是凭证）。
6. 跨租户：用 A 租户用户的令牌读 B 租户的会话 id 返回 **404**（查不到属主时 fail-closed，
   刻意不用 403 —— 403 与 404 的差异会变成"这个 thread_id 存在吗"的枚举探针）。
   带一个与令牌不符的 `X-Tenant-Id` 则返回 **403**。
7. `GET /docs` 返回 404。
8. 反代场景下 `TRUST_PROXY_HEADERS=1`，并用不同来源 IP 验证限流是分别计数的。
9. `LLM_MAX_TOKENS_PER_REQUEST` 与 `USER_DAILY_TOKEN_QUOTA` 已设为非 0。
10. `/health/ready` 的四项检查全部为 ok：llm、db、vector_store、checkpointer。
11. `checks.checkpointer` 显示为异步持久化的检查点，而不是内存实现。
12. `python -m app.migrations --status` 退出码为 0。
13. `python scripts/pg_backup.py drill` 能跑通。
14. `POSTGRES_PASSWORD` 已改成强口令。
15. 数据库端口仍是回环绑定。
16. 对外入口走 TLS 配置（443 加 HSTS），而不是只开明文 8080。
17. `/metrics` 能抓到请求量、token 与待审积压指标。
18. 告警规则已加载，且待审积压有「长时间大于 0」的告警。
19. 审核通知 webhook 已配，且走一次低分对话确实收到通知。
20. 多副本时 `REDIS_URL` 已配，且额度在副本之间确实共享。
21. 镜像构建 job 全绿。
22. 忽略清单里没有**无到期日**的条目——没有到期日的忽略等于永久忽略。

## 常见故障与排查

### 回答里没有任何引用

最可能的原因是**语料为空**。服务会为此打一条明确的告警日志。
容器部署时优先检查语料目录是否挂载、路径是否与 `DOCS_DIR` 一致——
镜像刻意不打包 `data/`，只带镜像不挂卷就会出现这种情况。

### 状态在重启后丢失

看 `/health/ready` 的 checkpointer 项。如果显示为内存实现，
说明 `DB_URL` 没配，或者异步检查点装配失败而降级了（此时启动日志里有 warning）。
判断「持久化到底有没有接上」，这一项是唯一可靠的信号。

### SSE 连上了但一个 token 都没吐

典型原因是检查点用了同步实现。同步的 PostgresSaver 没有异步查询接口，
异步调用会在流的中间抛 `NotImplementedError`，表现成「SSE 连上了、零 token 就被 error 收尾」，
很难往检查点上想。必须使用异步的检查点实现。

### 客户端断开后服务仍在生成

止损依赖 sse_starlette 的客户端关闭回调。不要改成轮询连接状态：
`receive()` 是单消费者通道，库自己的监听任务已经独占消费，
轮询永远晚一步，表现成「生成确实被取消了，但断开计数器恒为 0、日志一行没有」。
回调必须是 async 的、不等待耗时操作、不关闭上游生成器。

### 探针全绿但服务实际不可用

注意探针的分工：存活探针不依赖任何外部服务，就绪探针才真探 LLM 配置、数据库与向量后端。
排障时应该看就绪探针，而不是只看存活探针。

### 告警规则在面板上 firing，但没人收到通知

检查 `prometheus.yml` 是否配置了 `alerting.alertmanagers`。
缺了它，规则照样 firing 并显示在面板上，但事件从不外发。
另外检查 Alertmanager 的 `receivers` 字段是否拼写正确——拼错是静默故障，不报错但路由全失效。
